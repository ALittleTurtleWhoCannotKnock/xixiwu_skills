# Grill With Docs

## 触发信号

- 用户描述了一个新功能或变更需求
- 需求中存在歧义或隐含假设
- 需要建立团队共享的领域语言

## 核心 Discipline

1. **追问直到无歧义** — 设计树的每个分支都必须有明确答案
2. **识别领域术语** — 在对话中捕捉项目特有的概念和 jargon
3. **维护 CONTEXT.md** — 将对齐后的术语定义写入项目文档
4. **先重述真实问题** — 对关键需求/方案，先做一次轻量钢人论证（重述真正想解决的问题 → 双向论证 → 找关键变量），确认对齐的是"真问题"而非表面描述。"关键"按全局 AGENTS.md 的判定标准（跨模块影响 / 多方案权衡 / 影响非目标 / 与架构冲突 / 改用户可见行为 / 不可逆）

## 操作步骤

### Step 1: 启动追问

用户描述需求后，立即开始追问。每次追问聚焦一个分支，直到该分支无歧义。

**追问框架：**
- 这个功能的边界是什么？（什么不做）
- 涉及哪些角色/权限？
- 数据量级和性能要求？
- 错误场景和异常处理？
- 与现有系统的交互点？

### Step 2: 识别并确认术语

在对话中识别项目特有的术语，向用户确认定义：

```
我注意到几个术语需要确认：
1. "导出" — 是指生成文件下载，还是仅数据查询？
2. "批量" — 具体数量级是多少？100、1000、还是 10000？
```

### Step 3: 更新 CONTEXT.md

对齐完成后，将确认的术语写入项目根目录的 `CONTEXT.md`：

```markdown
# CONTEXT.md

## 术语表

### Export
**定义**: 管理员触发，将用户数据生成为 CSV 文件，异步处理后邮件通知下载
**边界**: 仅支持 CSV，不支持 Excel；单文件最大 10 万行
**相关模块**: exports, csv-generator, notification

### Materialization Cascade
**定义**: 当课程被"发布"时，其下所有章节和课时自动获得文件系统实体
**触发条件**: 课程状态从 draft 变为 published
```

### Step 4: 确认对齐完成

向用户总结：
- 需求边界（做什么、不做什么）
- 关键决策点及结论
- 已更新的 CONTEXT.md 内容

## 产出物

- 无歧义的需求描述
- 更新的 `CONTEXT.md`（项目领域词典）

## 下一步

需求对齐后，进入 `/to-spec` 阶段，将对话转化为结构化 spec。
