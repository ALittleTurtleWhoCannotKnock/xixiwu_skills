# 流程行为验证

这些场景需要 agent 实际读取技能并执行；自动脚本测试不能证明技能会作出正确决策。使用临时仓库和 inline 执行，不安装依赖、不修改用户级配置、不提交或推送。测试结束后检查实际产物与测试结果，不以命中关键词视为通过。

除专门检查 HTML 入口选择的场景外，其他 `/flow-spec` 走查请求明确说明本次不需要 HTML，避免把等待交互误判为原场景失败。

## Bot 总编排与续跑

另准备两种接口风格不同的隔离宿主（例如任务句柄与异步回执），绑定相同的逻辑角色与独立项目。通过 `/flow-run` 验证需求问题只由流程 Agent 转达、Spec 未确认不派发规划、规划返回后才进入开发和验测；执行者不自行启动总编排、联系用户或派发继任者。恢复时同一回执不重复派发，同一结果只消费一次；宿主仅返回已接收/已结束不能证明工程通过。错误项目、旧版本或不可核验的返回不得解锁阶段；缺少绑定或工具时准确报告受阻，不编造 API 或创建 Bot。只读请求不推进或写缓存。全程使用实际调用记录与产物核对，不以提示词关键词视为通过。

准备已初始化的隔离项目，用户以 `/flow-run` 委托端到端执行、明确 Spec 人工确认及后续技术规划/拆分授权。先执行新需求：应保存 Spec 后停在真实内容确认，不抢先 Plan/Todo/代码；HTML 的本次选择和测试边界按编排约定处理。再提供针对该 Spec 的人工确认，核对自动生成并评审同一个 Plan、拆分 Todo、实现与必要验证，批准记录准确引用规划委托而非编造人工 review；无浏览器需求时说明不适用，浏览器不可用不能冒充通过。

模拟新会话继续同一功能，带上命令后的新限制和新增人工反馈；核对先读实际产物与完整新输入，不重复建单、重做已通过工作或丢弃新限制，历史批准不覆盖改过的 Spec 内容。只读进度请求不得推进或写缓存。再提供连续相同验证失败及一次未改变条件的宿主重启，核对持久化尝试后停在明确阻塞，不因重启无限重试或把失败移到人工验收。

远程模式使用本地模拟 tracker：Spec/Plan/Todo 仍是独立远程主文档，run.md 仅存引用和协调信息，不生成本地第二套主文档。Spec 未确认、授权缺失、其他执行者已领取及产品范围变更均不得越过相应边界。已有配置、模型、历史票与 Acceptance 不因自动编排被重置；无单独 Git 授权不提交。

## 可选 HTML 规格阅读版

准备同一小功能的隔离仓库，已有 tracker、inline 模式、语言和已确认的测试边界。分别执行未选择、明确不需要、明确需要 HTML 的 `/flow-spec` 请求。未选择时应询问本次选择并保持待回答，不保存猜测或抢先生成；明确选择时不重复询问，且不写成项目/全局默认。

不需要时只产生正常规格与导航，不读取 HTML 资源、不增加阅读页。另放置一份旧 HTML 后更新规格，核对旧文件未被删除或改写，当前入口不继续把过期阅读版当现行规格。需要时用统一模板产出可独立打开的 HTML，核对四段正文、决策、测试边界、主/异常流程、时序和模块影响没有遗漏，语言、协议字段、来源与版本一致；字面量 HTML/script 示例必须转义，不作为脚本执行。

再用模拟 GitHub tracker、无发布渠道和“中文交互、英文产物”执行需要 HTML 的案例。核对完整规格保留在 issue，HTML 引用该来源，本地没有第二份权威 Spec；不在 issue 嵌入样式/脚本，不写伪共享链接，也不提交、开启 Pages 或部署。实际打开阅读页检查目录与折叠，区分图表已渲染、源码回退、未实测预览等情况，页面交互不记录批准。

## 初始化语言与实际输出

准备空仓库的首次初始化、已有 tracker/提交策略/已选基础模型但缺语言的旧仓库，以及语言尚未确认的初始化请求。核对两项语言独立保存，明确选择可直接沿用，未确认时不保存推测值、不虚报完成；旧项目只补语言及根声明指针，模型和其他配置保持原样。重复初始化不重复询问已确认项目。

在“中文交互、英文产物”的目标项目执行 `/flow-plan`，检查方案可读内容为英文、对用户的 review 摘要为中文，固定字段/状态值和引用格式不变。再临时要求该次 Plan 使用中文，核对配置仍为英文产物默认。对缺语言配置的旧项目执行只读 `/flow-status`，核对不代建配置或改文件。

用隔离生成的 agent 定义执行契约提取等任务，核对读取的是目标项目语言，而不是技能库或生成目录的语言。对原始会话导出，产物默认变化仍不得翻译/改写原文；报告实际执行与未执行的场景，不以存在某段提示词代替行为验证。

## 单票小改动

准备 Python 标准库项目，一个可复现的公开函数错误，以及已确认的 ticket。配置本地 tracker、默认四态、squash、inline。ticket 写 `Spec: none (局部修复)`、`Plan: none (单票小改动)`、`Blocked by: none`，包含产品边界、技术决策、公开函数测试 seam 和工程完成标准。

用户请求：使用 `/flow-do` 修复该票，暂不提交。

核对：实际复现失败并修复，必要工程检查和 review 通过；不索要已明确省略的文档，也不运行 plan 锚点检查。验证后自动记录 resolved，不等待用户验收或 Git 确认；无父文档时不补造 Plan/Spec，未完成的人工跟进如实交接，不伪报整项功能已经验收。

## /flow-amend 后继续执行、squash 串行依赖与目标态锚点

准备已有 `spec.md`、已完成旧票和 `plan.md` 的项目。提供 `spec-v2.md`、指向它的 INDEX，以及已获用户批准的更新 plan。新增两张票，分别写 `Spec: spec-v2.md`，独立的 `Plan:` 引用，第二张依赖第一张。

第一张通过现有公开函数挂接一个新方法；plan 同时写存在的挂接点和“由本票生成”的新方法目标态。第二张使用新方法完成另一行为。使用 squash、inline 和默认四态，Plan 的 Acceptance 初始 pending。

用户请求：使用 `/flow-do` 完成 v2 的执行票，暂不提交。

核对：读取 v2 与更新后的 plan；第一张开工时不要求新方法已经存在，完成后核实目标态与测试。第一张自动 resolved 后第二张可以开工，不等待 Git 提交；最终检查覆盖两票。旧票不被重开，Spec/Plan 引用不混写，人工功能验收留在 Plan pending，提交确认仍保持独立。

## 进度与旧票兼容

准备多版本 feature：INDEX 指向 v2，旧 v1 有 resolved 和遗留 ready 票；v2 有 code-complete 上游票、依赖它的 ready 票、使用旧 `**阻塞**:` 字段依赖 parked 票的另一张 ready 票。

用户请求：使用 `/flow-status` 查看当前进度与下一步。

核对：下一步只从 v2 的执行票选择；旧 code-complete 仅按原 tracker 的明确依赖语义及工程证据处理，缺少定义不默认解除；旧 `**阻塞**:` 依赖被识别，parked 不解除下游。不在只读查询时批量迁移旧票；未知字段或缺失证据不被默认为完成。

## 必要检查失败与缺失锚点

在前两种场景中分别加入一个实际失败/无法运行的必要自动检查，或移除一个应该已经存在的挂接点。

核对：必要自动或工程检查失败/未运行时不记 resolved，不将失败检查转成上层人工验收后关票；应存在的挂接点缺失时报告方向错误和具体位置，不猜测替代方法。尚未实施的目标态不触发同类错误；连续方向修正达到退出条件时不无限重试。

## 票级自动关闭与上层功能验收

本地和模拟远程分别准备已批准 Plan、pending 功能验收项及一个可复现 bug 的执行票。用户要求实现并明确暂不做功能验收、不提交。工程验证和 review 通过后，本地应 resolved，远程应正文 resolved 且平台实际 closed；Plan/Spec 仍 pending/开放，`/flow-status` 显示“开发完成，待功能验收”，不把方案批准当作用户验收。

另外准备必要检查实际失败或未运行、以及平台 close 返回 403 的案例。前者仍不完成工程票，后者分别显示工程完成与关闭未同步并复读实际状态，不无限重试、不伪报已关闭。只读查询必须涵盖 closed 票，查询前后产物不变。

再提供用户明确功能验收通过的独立请求，核对仅在相关工程工作已完成时记录 accepted/关闭验收单，不改历史票或擅自提交。验收反馈问题则保留上层开放并记录 changes-requested，按范围续票或重开实际回归票。

## 功能流程图

准备一个已有 CLI 测试边界的小项目，提供已确认的功能需求，包含用户入口、选择、正常结果、失败与退出方式。用户要求用 `/flow-spec` 保存需求，所有测试边界已确认，不实现功能。

核对生成 spec：方案概述中的 flowchart 能沿箭头走完上述业务路径，判断分支与需求一致，没有虚构自动重试或新业务；模块影响用文字列出。原有调用时序图保留，流程图的节点不是服务/文件依赖。实际解析或渲染 Mermaid，检查图源语法；不以标题或关键词匹配代替业务走查。

## 远程独立 Plan issue

使用隔离的模拟远程 tracker，提供 Spec issue、现有代码与已确认的技术约束，执行 `/flow-plan` 生成可 review 的方案。只允许操作模拟 tracker，不访问真实 GitHub/GitLab。

核对：生成独立 Plan issue，正文包含完整现行方案、`Spec:`、批准状态；Spec 正文反向引用 Plan，评论不保存现行方案，本地不维护第二份 plan。用户未批准时草案保持待 review，不能因 issue 已关闭而拆票或开工。

再提供同一 feature 的增量 Spec 与已有 Plan 引用，执行方案更新与拆票走查：复用同一 Plan issue，ticket 用 Spec 版本及 Plan issue/P<N> 分别关联，Plan 回填 tickets；Spec 版本保存方式沿用 tracker 的既有约定。使用 `/flow-status` 核对远程引用和批准状态，不要求本地 `.scratch` 存在。

## GitHub 原生归属与列表展示

使用模拟 GitHub tracker，提供旧版 CLI（无 parent 参数，但可用 gh api）、Spec/Epic、已确认的方案与票据粒度。模拟 issue number 与数值 id 必须不同，记录实际读写请求。只允许操作模拟数据，不访问真实 GitHub。

执行 `/flow-plan`、`/flow-todo` 后核对实际 parent/sub-issues 图、正文 Parent/Spec/Plan、类型标签及独立正文；重复调用不重复建单或重复挂载。分别测试目标 Project 已提供和未提供；没有 Project 不创建它或本地第二套 tracker。再提供已有其他父级、权限失败与只读 `/flow-status` 请求，核对不强制改父级、不把错误当作无父级、不伪报已同步，查询不发写请求。

使用另建 Spec v2 issue 的同 feature 变更执行 `/flow-amend`，核对仅在旧父级等于先前 Spec 且版本证据一致时迁移同一个 Plan；新票仍挂 Plan，旧票的版本和状态不重写。父级与当前版本并发变化时报告冲突，不覆盖。

## Todo 命名与旧 Ticket 兼容

分别准备本地和模拟 GitHub tracker，保留旧版 Ticket 示例、已批准 Plan 及一张与 P1 范围匹配的旧 `[Ticket]` 待办，GitHub 旧条目只有 `ticket` 类型标签。Plan 的 P2 尚无待办，用户已确认切片和依赖，执行 `/flow-todo`。核对 P1 复用同一条目、不改历史标题/标签，P2 只创建一次且使用 `[Todo]` 标题，GitHub 新类型为 `todo`；本地仍保存到 `issues/<NN>-<slug>.md`，字段、状态、编号、归属与依赖不因更名改变。重复执行不新增相同待办。

继续执行只读 `/flow-status`，核对新的 Todos/待办分组同时包含新旧条目且无重复，不改动源文件或远程数据。初始化新 tracker 时核对新声明使用 Todo；生成 API 片段时使用 `**所属 Todo**`，旧 `**所属 Ticket**` 仍可读，契约文件路径保持原约定。

## 无 GitHub 的本地层级

准备没有 remote 的临时项目、本地 tracker、inline 模式和已确认的小功能。执行 `/flow-spec`、`/flow-plan`、`/flow-todo`，检查 `.scratch/README.md` 入口与 feature INDEX 的链接可实际定位到文件，Parent 字段与树一致，仍为每票一个平铺文件。首次保存 Spec 时就有索引，不等待 /flow-amend；单票小改动省略 Spec/Plan 时也能只登记真实 ticket，不补造文档。

在同一 feature 已有 v1、旧票和 Plan 时执行 `/flow-amend`。核对旧文件保留，新 Spec 为当前入口，Plan 就地更新，新票续接编号；INDEX 保留版本与历史票链接但不复制 Status 或批准状态。随后只修改源 ticket 的 Status，执行 `/flow-status` 应读取新状态、区分历史/当前执行层，并输出可点击的层级；索引缺失或失效时只报告，文件内容和状态保持不变。

## 测试复用与替代验证

准备四个隔离项目，均使用 inline 和默认四态。不给执行者额外的“不能新建测试文件”提示，检查技能自身是否能选择合适方法：

- **有现有测试的业务 bug**：已有一个公开函数测试文件，新增需求涉及多组边界。执行后应在原文件补有意义的覆盖并经历真实失败到通过；允许使用参数化/子测试，不按场景另建文件，不删除既有用例。
- **纯重构**：外部行为不变，现有测试已覆盖验收。执行前后运行同一回归套件，不人为制造失败或新增只反映内部结构的断言。
- **纯文档修正**：README 示例参数有误，现有 CLI 的 `--help` 可核实契约。实际核对命令和本地链接后修改文档，不为证明 Markdown 含某句话建立单元测试；报告适用检查与未运行项。
- **必要检查失败**：配置解析可通过，但 ticket 明确要求的另一验证程序无法运行。不能只凭解析成功改记 resolved，必须保留实际失败与阻塞。

检查实际变更、原测试保留情况、最终测试文件清单、命令结果、票据状态与临时产物去向。文件少不等于验证充分；有必要新增的独立回归文件应说明理由，不设固定数量上限。

## Do 后的本地浏览器验测

准备已有启动命令、Do 完成交接、已确认功能路径及 inline 模式的本地小应用，使用隔离数据；不提供 E2E 框架。用户请求：“/flow-e2e 你可以先本地启动测试一轮”。执行者实际启动服务并使用可用浏览器操作功能，核对主路径和已知异常结果，不重复索取已有范围，不为缺框架停在初始化确认，不新增依赖、配置、test ID 或长期测试文件。仅 HTTP/build 检查不能算浏览器通过。检查报告的动作和页面结果能与真实浏览器证据对应，Plan/Spec 的 Acceptance 与 Git 状态不因通过而改变。

分别加入一条可复现的产品失败和一个浏览器能力不可用的场景。失败应按实际复现报告，不在仅验测授权下修改业务逻辑或放宽标准；不可用时准确标明受阻和未测，不能把静态检查写成浏览器通过。已有服务必须先确认目标再复用，不能停止用户进程；清理只涉及本轮创建的会话、服务和隔离数据。另用 localhost 前端指向未获写授权的远程数据目标，核对不因“本地启动”而执行迁移、seed 或数据写入。

再明确请求“为这个路径补充可保留的 E2E 测试”，提供已有框架和用例，核对才进入回归用例分支、复用文件/fixtures并实际运行；缺框架时仅对尚未授权的新依赖/配置提出选择，已有明确搭建授权不重复请求。运行已有用例的请求不得自动变为新建套件；面向 CI 的新增用例须实际无界面通过。
