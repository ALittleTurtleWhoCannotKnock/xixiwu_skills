# 流程行为验证

这些场景需要 agent 实际读取技能并执行；自动脚本测试不能证明技能会作出正确决策。使用临时仓库和 inline 执行，不安装依赖、不修改用户级配置、不提交或推送。测试结束后检查实际产物与测试结果，不以命中关键词视为通过。

## 单票小改动

准备 Python 标准库项目，一个可复现的公开函数错误，以及已确认的 ticket。配置本地 tracker、默认五态、squash、inline。ticket 写 `Spec: none (局部修复)`、`Plan: none (单票小改动)`、`Blocked by: none`，包含产品边界、技术决策、公开函数测试 seam 和验收标准。

用户请求：使用 `/implement` 修复该票，暂不提交。

核对：实际复现失败并修复，必要测试通过；执行不索要已明确省略的文档，也不运行 plan 锚点检查。验证后记录 `code-complete` 和待处理 checkpoint，不因未提交而伪报测试失败，也不跳过最终验收直接报全部完成。

## amend 后继续执行、squash 串行依赖与目标态锚点

准备已有 `spec.md`、已完成旧票和 `plan.md` 的项目。提供 `spec-v2.md`、指向它的 INDEX，以及已获用户批准的更新 plan。新增两张票，分别写 `Spec: spec-v2.md`，独立的 `Plan:` 引用，第二张依赖第一张。

第一张通过现有公开函数挂接一个新方法；plan 同时写存在的挂接点和“由本票生成”的新方法目标态。第二张使用新方法完成另一行为。使用 squash、inline 和默认五态。

用户请求：使用 `/implement` 完成 v2 的执行票，暂不提交。

核对：读取 v2 与更新后的 plan；第一张开工时不要求新方法已经存在，完成后核实目标态与测试。第一张达到 `code-complete` 后第二张可以开工，不等待 Git 提交；最终检查覆盖两票。旧票不被重开，spec/plan 引用不混写，待人工验收和 checkpoint 保持可见。

## 进度与旧票兼容

准备多版本 feature：INDEX 指向 v2，旧 v1 有 resolved 和遗留 ready 票；v2 有 code-complete 上游票、依赖它的 ready 票、使用旧 `**阻塞**:` 字段依赖 parked 票的另一张 ready 票。

用户请求：使用 `/find` 查看当前进度与下一步。

核对：下一步只从 v2 的执行票选择；code-complete 依赖可解除但有待验收提示；旧 `**阻塞**:` 依赖被识别，parked 不解除下游。未提交的旧票、未知字段或缺失证据不会被默认为完成；文件与状态保持不变。

## 必要检查失败与缺失锚点

在前两种场景中分别加入一个实际失败/无法运行的必要自动检查，或移除一个应该已经存在的挂接点。

核对：必要自动检查失败或未运行时不记 code-complete/resolved；应存在的挂接点缺失时报告方向错误和具体位置，不猜测替代方法。尚未实施的目标态不触发同类错误；连续方向修正达到退出条件时不无限重试。

## 功能流程图

准备一个已有 CLI 测试边界的小项目，提供已确认的功能需求，包含用户入口、选择、正常结果、失败与退出方式。用户要求用 `/to-spec` 保存需求，所有测试边界已确认，不实现功能。

核对生成 spec：方案概述中的 flowchart 能沿箭头走完上述业务路径，判断分支与需求一致，没有虚构自动重试或新业务；模块影响用文字列出。原有调用时序图保留，流程图的节点不是服务/文件依赖。实际解析或渲染 Mermaid，检查图源语法；不以标题或关键词匹配代替业务走查。

## 远程独立 Plan issue

使用隔离的模拟远程 tracker，提供 Spec issue、现有代码与已确认的技术约束，执行 `/to-plan` 生成可 review 的方案。只允许操作模拟 tracker，不访问真实 GitHub/GitLab。

核对：生成独立 Plan issue，正文包含完整现行方案、`Spec:`、批准状态；Spec 正文反向引用 Plan，评论不保存现行方案，本地不维护第二份 plan。用户未批准时草案保持待 review，不能因 issue 已关闭而拆票或开工。

再提供同一 feature 的增量 Spec 与已有 Plan 引用，执行方案更新与拆票走查：复用同一 Plan issue，ticket 用 Spec 版本及 Plan issue/P<N> 分别关联，Plan 回填 tickets；Spec 版本保存方式沿用 tracker 的既有约定。使用 `/find` 核对远程引用和批准状态，不要求本地 `.scratch` 存在。

## 测试复用与替代验证

准备四个隔离项目，均使用 inline 和默认五态。不给执行者额外的“不能新建测试文件”提示，检查技能自身是否能选择合适方法：

- **有现有测试的业务 bug**：已有一个公开函数测试文件，新增需求涉及多组边界。执行后应在原文件补有意义的覆盖并经历真实失败到通过；允许使用参数化/子测试，不按场景另建文件，不删除既有用例。
- **纯重构**：外部行为不变，现有测试已覆盖验收。执行前后运行同一回归套件，不人为制造失败或新增只反映内部结构的断言。
- **纯文档修正**：README 示例参数有误，现有 CLI 的 `--help` 可核实契约。实际核对命令和本地链接后修改文档，不为证明 Markdown 含某句话建立单元测试；报告适用检查与未运行项。
- **必要检查失败**：配置解析可通过，但 ticket 明确要求的另一验证程序无法运行。不能只凭解析成功改记 code-complete，必须保留实际失败与阻塞。

检查实际变更、原测试保留情况、最终测试文件清单、命令结果、票据状态与临时产物去向。文件少不等于验证充分；有必要新增的独立回归文件应说明理由，不设固定数量上限。
