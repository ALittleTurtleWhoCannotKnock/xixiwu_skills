# Multica adapter

Source baseline: [multica-ai/multica](https://github.com/multica-ai/multica), revision `3c5c8b245359b9b8e913a47f97211f2a3426f149`. This is optional host guidance; logical roles and stage methods remain host-neutral.

## Install methods and bind identity separately

Use the self-contained `dev-flow.skill` distribution with `multica skill import --file`, then add its returned skill ID to the actual agent. A local `npx skills add` or CLI skill symlink is not a Multica workspace import. Workspace packages are snapshots; source updates do not refresh archive imports automatically.

The display description does not enter the execution prompt. Put the selected role in the agent's persistent **Instructions** field. The repository's Multica install target imports one package, adds that binding without deleting other skills, and maintains a marked role-instructions block while preserving custom instructions outside it. Review old custom rules for contradictions; never claim the package alone reconfigured the agent.

The `flow` role is coordinator-only even when the method library includes implementation guides. Missing specialists do not enable inline coding. Other profiles are Requirements, Planning, Development and Verification. Agent Access is an invocation allowlist, not a command/filesystem permission boundary. The official [configuration guide](https://github.com/multica-ai/multica/blob/3c5c8b245359b9b8e913a47f97211f2a3426f149/apps/docs/content/docs/agents-create.zh.mdx) and [security model](https://github.com/multica-ai/multica/blob/3c5c8b245359b9b8e913a47f97211f2a3426f149/apps/docs/content/docs/security-model.zh.mdx) describe these different layers.

## Use the actual host dispatch and return contract

For a five-role squad, use the [Chinese squad policy template](../assets/multica-squad.instructions.zh-CN.md). Replace its five role placeholders with actual, verified workspace members and select the Flow Agent as leader. Create only the intended squad, add the four specialists with descriptive roster roles, save the rendered instructions, and read back leader/membership/instructions before assigning work. The leader normally becomes a member automatically; verify this rather than adding duplicates. The template configures routing and confirmation policy, not tool permissions or scheduled execution.

Read Multica's injected runtime brief and actual CLI help. During a managed run, use the executable supplied in `MULTICA_CLI_PATH` as instructed by that brief rather than choosing a possibly older CLI from PATH. Use the current project/workspace and actual agent/squad IDs; do not apply PI-Bot's message_bot or ask_user APIs here.

For persistent multi-agent issue workflows, a configured Multica Squad supplies a native coordinator path: designate the Flow agent as leader and bind the specialists as members. The leader delegates with the exact mention links provided by the squad roster, records its squad activity, and follows the host's re-triggering protocol when members report. Plain `@name` text is not sufficient. Do not create a squad, change Access, or add members merely because the method library is installed; ask for missing bindings or use an already authorized team.

Choose one dispatch trigger for a unit of work: a delegation mention on the parent issue **or** assignment of its child issue. Combining both can launch the same work twice. Stage parking/promotion and dependency checks must follow the actual tracker and host protocol, not assumed local status values. Human Spec confirmation stays with the Flow agent; a squad/member update cannot supply it. A direct assignment to the Flow agent is not a native squad-leader run: check the actual task identity before using squad-only briefing, activity or return behavior.

Generic background tool handles have a different lifetime: Multica's ordinary top-level run ends when its turn exits and does not provide a background-completion wakeup. Do not launch run-owned work in the background and yield while claiming its result will resume you. Use a supported foreground call that actually collects results, or an explicitly configured persistent issue wakeup/native Squad mechanism. Follow host-required recovery and activity/status rules; a generic skill cannot waive them.

These behaviors are described in the [Squad guide](https://github.com/multica-ai/multica/blob/3c5c8b245359b9b8e913a47f97211f2a3426f149/apps/docs/content/docs/squads.mdx) and [runtime brief](https://github.com/multica-ai/multica/blob/3c5c8b245359b9b8e913a47f97211f2a3426f149/server/internal/daemon/execenv/runtime_config_sections.go). Inspect actual artifacts and check results regardless of task/issue completion messages. A private capability-introduction chat is not evidence that a Squad or tool restriction is configured.

## Todo groups and execution contexts

Apply the [generic grouping rules](team-mode.md) to Spec → independent Plans → simple Todos. The Planning agent chooses peer scopes/count unless the user specifies them; a P<N> package is not another Plan. Bind every native execution issue/task to its actual Plan/Scope and applicable Spec/Todo references. A waiting or changed peer does not reset an unaffected approved scope. Keep the declared tracker authoritative: when GitHub owns the artifacts, Multica execution issues carry links, assignment/results rather than another Spec/Plan/Todo body master.

Small related Todos within a Plan may share a session/checks; independent groups/Plans may use distinct native tasks and isolated contexts. Reuse existing agent roles/configuration rather than making one Bot per Plan. Several peer Plans are not serial workflow stages: do not introduce stage barriers that make one new Plan depend on another. A coordinator merges the full Plan registry from returned scoped references; separate writers must not overwrite it with only their own Plan.

Use only the host's actual child-task/session capabilities. Assigned executable child issues already trigger their agent; do not also mention it on the parent for the same work. Park dependent work until its declared prerequisites hold. Pass each worker only its bounded scope, actual authority and relevant references. Completion, actionable questions/blockers and host limits need a return; routine progress and already-consumed results need no additional public acknowledgement loop beyond required host logging.

The CLI and [project-resource guide](https://multica.ai/docs/project-resources) distinguish `in_place` (same-directory runs serialize) from isolated `worktree` execution. Agent concurrency limits alone do not remove directory locks. Worktree delivery creates local Git commits; verify the runtime's capability and compatibility with the project's commit authorization before changing resource modes. Preserve existing resources, models and permissions; do not switch modes merely because a group could be parallel. Inspect the groups' actual code and required checks before integrated verification, regardless of native run/issue completion.

## Optional workflow for the five-role squad

Workflow guidance was checked against Multica revision `61e7e8f966f53478f3efe68ec50c5a5fdd00a51f` and CLI 0.8.0. The server [rejects squad and creator step handlers](https://github.com/multica-ai/multica/blob/61e7e8f966f53478f3efe68ec50c5a5fdd00a51f/server/internal/issueworkflow/issueworkflow.go), although some CLI help and type declarations still list them. Keep the issue assigned to the squad; use No handoff columns for stage visibility and let its leader coordinate the specialists. Assigning each column to a specialist would change the parent assignee and its squad context.

Create a separate named workflow from [the step template](../assets/multica-workflow.steps.json). Its five product-stage columns are 需求与规格 → Spec 待确认 → 方案与待办 → 开发实现 → 集成验测, followed by in_review for functional acceptance. All seven built-in statuses remain available for engineering Todos, blockers and existing issues. The engineering path is todo → in_progress → done after implementation, required checks and review, while the feature parent stops at in_review for functional acceptance. Explicit next-status references keep engineering Todos out of the feature-stage chain. New status names belong to the workspace's shared status library; do not rename existing shared statuses to customize one project's board.

After creation, read back the workflow and resolve the actual generated status keys. Render [the Chinese squad workflow instructions](../assets/multica-workflow.instructions.zh-CN.md) with its name, ID and verified stage-key mapping, back up the squad's existing instructions, and maintain one separate `dev-flow-workflow` marked block. Preserve other instructions and squad settings. These instructions keep Spec confirmation, parent acceptance and engineering Todo closure distinct; workflow columns alone do not enforce those decisions.

Create only the requested workflow. Switch a project only when its target is authorized, first using `multica project workflow set <project-id> <workflow-id> --dry-run`; inspect status mappings and verify the saved project workflow afterward. Creating the workflow and switching a project do not prove actual dispatch, confirmation or verification works. A No handoff column keeps the assignee and starts no run: after moving between active stages, the leader continues the next dispatch in the current turn rather than waiting for a nonexistent automatic wakeup. See the [official workflow guide](https://multica.ai/docs/workflows).

## Environment boundary

Role instructions constrain intended behavior; they do not remove coding tools from the underlying harness. Multica's documented default runtime grants the daemon user's filesystem privileges and does not promise a filesystem sandbox. If a deployment needs a coordinator that cannot write application code even if instructions are ignored, arrange an actual host/runtime/OS boundary and verify it independently. Do not describe prompt compliance, disabled Skill discovery, or Access settings as that boundary.

This repository does not silently change sandbox, approval, model, token, MCP or OS settings. Source review, archive validation and simulated CLI tests do not prove a live workspace's enforcement or end-to-end Squad operation.
