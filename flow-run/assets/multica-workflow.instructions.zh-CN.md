## 主任务如何推进

- 只管理确实归本小队的协调主任务。新需求先进入「需求与规格」，交需求成员执行 flow-clarify／flow-spec；有已有产物时从第一个未满足阶段恢复。不要把仍需确认的主任务当成工程 Todo 直接关闭。
- Spec 草案保存后，队长展示实际内容／版本和测试边界，移入「Spec 待确认」并等待用户答复，结束本轮。这个停留是有意等待，不能因本轮结束或宿主建议的下一列而自动进入规划。保持小队归属，让用户的后续回复由原小队继续处理；收到含糊回复时只补齐真正缺失的确认。
- 只有取得用户对当前 Spec 内容／版本的有效确认后，才能进入「方案与待办」，携带确认来源和范围内自动规划授权，交方案成员执行 flow-plan＋flow-todo。状态被手动拖动、成员转述或列名本身不提供产品确认与执行授权；缺证据就回到待确认，不先派发下游。
- 方案成员按 AI 判断或用户指定数量，将 Spec 划为互不依赖的实际 Plan；每个有独立 Scope、批准／验收和简单 Todo。用户数量优先，不能以包编号或空壳代替；确有独立性／覆盖冲突则说明后询问。读取全部 Plans／旧 Plan 引用，不把第一份方案当全体。
- 选定 Plan 的产物、依赖及批准核对通过后可进入该范围开发，另一 Plan 待审／受阻不拦住它。按同 Plan 的上下文和依赖合批简单 Todo，独立范围在宿主／目录隔离允许时并行；用户选择部分 Plan 时不顺带启动其余。队长可直接维护流程字段、确认来源与导航，不为此单独派人。保留已完成工作和合法的小改动省略路径。
- 某 Plan 的工程 Todo 通过必要检查后，可先做其范围的集成验测／验收；不同 Plan 结果分别记录，真正 Spec 全局检查待其输入就绪后执行。主任务单列只是总体焦点，不能代替各 Plan 的实际状态。失败仅回到受影响范围修复／重验，范围变化回 Spec 确认；真实阻塞仍如实报告。
- 主任务所覆盖的各 Plan 与全局工程检查、适用验测达标后，队长将主任务移到 in_review，给用户交付证据与 Plan／Spec 验收入口，然后等待功能验收。不得自行将主任务改为 done 或把 Acceptance 写为 accepted；须有真实功能验收或适用的既有授权集成。

## Todo 与异常

工程 Todo 继续使用 backlog／todo／in_progress／in_review／done 等原生工程状态，在实现、必要检查、review 与交付物通过后，由派发约定的单一状态写入者（flow-do 监督者或核对证据后的队长）同步关闭。合批不合并票的权威记录，共用检查仍须覆盖每票，分别报告通过／失败／未测；不逐张要求用户功能验收，也不让每张 Todo 重走主任务的五阶段。Spec／Plan 等产物问题按其真实用途处理，不因处于工程状态而自动视作 Todo。

主要拆解落实为 Spec → 独立 Plans → 简单 Todo，不靠额外内部任务层承载大 Todo。Todo 可聚焦某条规则、某个工程层或验证结果，准备好输入、边界和检查；常规代码步骤留在票内，相关小票可合批。每票绑定唯一实际 Plan／监督者／状态写入者，部分结果不关闭整票，未定业务或架构选择先回负责人。变更只影响相关 Plan，未变范围须有沿用依据，不重置其原批准／验收。

本节替代通用小队说明中“主任务工作期间始终 in_progress”的状态约定：主任务工作期间保留其真实阶段列，专业成员不改主任务状态。No handoff 换列不会自动续跑；队长换列后应在当前回合继续派发下一阶段，只有等待用户、已派发成员、受阻或宿主限制时才结束本轮。继续遵守单次派发、回执去重、有限重试、环境与数据边界以及独立的 Git／部署授权。
