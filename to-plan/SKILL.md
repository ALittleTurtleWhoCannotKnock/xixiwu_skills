# To Plan

## 触发信号

- Spec 已通过 `/to-spec` 确认
- 即将进入 `/to-tickets`，但需要先拍死技术方案（用什么、怎么做、风险在哪）
- 想在拆票前 review 一遍方案，**审过才让 agent 实现**（这是"放心放手"的卡点）

## 核心 Discipline

1. **技术决策归 plan** — spec 只管产品意图与边界；技术选型、算法、实现路径等工程师内部决策，**在 plan 拍死**，不在 spec
2. **plan review 是人工卡点** — **必须经用户批准才进 `/to-tickets`**。这是用户说"放心让 agent 按 plan 直接实现 ticket"的兑现点，不能跳过
3. **plan 是单一现行文档** — `plan.md` 就地更新，不做 `plan-vN` 版本文件。"为什么变"的追溯留在 spec 的 amend 记录里；"现在怎么做"以 plan 现状为准
4. **风险前置** — 把不确定项（待实测、待外部确认的断言）明确列出，不让它们藏进实现细节里

## 操作步骤

### Step 1: 侦察代码上下文（可复用 scout）

若 `/to-spec` 阶段已产出 `.scratch/<feature-slug>/context.md`，直接读取复用，无需重复侦察。若不存在且需要更细的代码理解（关键文件、现有工具函数、可复用模式），按 execution-mode 分派 `scout` 补侦察（只读不改）。

### Step 2: 合成实施蓝图

产出 `.scratch/<feature-slug>/plan.md`，结构如下：

```markdown
# <Feature> 实施蓝图（plan.md）

## Context

[为什么做这个 feature——从 spec 的产品意图引述，一两句。链接 spec 位置]

## 技术决策表

| 决策点 | 选项 | 选择 | 理由 |
|-------|------|------|------|
| [技术选型/算法/路径] | A/B/C | [选择] | [为什么——含被否方案的简短理由] |

## 包分解

### P1: <包名，对应一张或多张 ticket>
**大致做什么**：[一句话——用户/功能视角的交付物]
**用什么技术**：[库/算法/模式，引用技术决策表的决策]
**怎么实现**：[实现路径概述——分几步、每步产出什么，**不写执行细节**]
**改动锚点**：[`文件#方法名`，标目标态（prefactor 之后的架构），一锚点一行，多个用 `/` 分隔。CREATE 型改动写"挂接点"（现有代码里挂钩子的方法），不写"新建文件 X"。格式硬约束：禁行号、禁代码体、禁伪代码——只说"在哪、变成什么行为"，"写什么代码"留给 implementer]
**关键文件**：[预期修改/新增的文件路径]
**复用点**：[可复用的现有函数/工具，带路径（有则列，无则省略）]
**风险点**：[这个包可能踩的坑——性能、边界、兼容性]

### P2: ...
```

**包分解的粒度边界（关键，防和 ticket 重复）：**
- plan 的包回答 **"做什么/用什么/怎么实现/风险"** ——方案层
- ticket 回答 **"在哪个 seam 测、改哪个文件哪段、测试用例是什么、验收标准"** ——执行层
- **方案细节不写进包**（那是 ticket 的活）；**执行细节不写进 plan**（那是拆票时的活）
- **改动锚点是唯一的定位事实源**：方法名只写在 plan 的"改动锚点"字段（ticket 通过 `**来源**: plan P<N>` 引用，不复述）。amend/Step 3.5 发现方法改名/挪位时就地更新锚点，避免双写腐化

**plan 条目与 ticket 的对应关系：默认 1:1，允许 1:N**（一个包拆多张 ticket）。ticket 头部标 `**来源**: plan P<N>`，指向 plan 条目，不复述方案。

### Step 3: 风险与验证策略

- **风险点**：每包的"风险点"字段 + 全局风险（跨包的，写在包分解之后）——如"低端机扛不住更高分辨率"这类**未经受控实测的断言**，明确标为待验证
- **验证策略**：整体端到端怎么验（在哪些 seam 交界处验证、关键集成场景）。每包内部的测试用例是 ticket 的事，plan 只管"这一包做完整体怎么知道它是好的"

### Step 4: plan review（人工卡点，必须过）

展示 plan.md 给用户 review：

- 技术选型是否认可（决策表的"选择"列）
- 包分解粒度是否合适（太粗会拆不出细节、太细会挤占 ticket 职责）
- 风险点是否识别全

**用户批准后才进 `/to-tickets`。** 用户要求调整则修改 plan.md 后重新 review；**用户未批准不得拆票**。

### Step 5: 保存并交接

- 保存 `.scratch/<feature-slug>/plan.md`
- **plan 头部加批准状态戳记**（find 读此状态判断阶段）：`**状态**: 已批准（<日期>）` 或 `**状态**: 待 review`
- **产出物即输入**：`/to-tickets` 读 plan 的包分解拆 ticket；`/implement` 读 plan 的技术决策理解"为什么这么做"；`/amend` 时 plan.md 就地更新

## plan.md 的边界

| 适合 | 不适合 |
|------|--------|
| 技术选型（用什么库/算法/路径） | 产品意图、边界、非目标（→ spec） |
| 实现路径概述 + 风险点 | 执行细节（seams/测试用例/文件行级改动 → ticket） |
| 跨包的全局技术决策 | 单包的测试用例清单（→ ticket） |

## 边界

| 适合 | 不适合 |
|------|--------|
| spec 已确认、即将拆票的场景 | 需求未对齐（先 `/grill-with-docs`） |
| 技术方案需要人工审过的场景 | 小改动一张票就完（直接 `/to-tickets`，无需 plan） |

## 与其他技能的关系

- **输入**：`/to-spec` 的 spec（产品意图与边界）+ context.md（可选）
- **输出**：`plan.md`（技术蓝图，含方法级改动锚点）→ `/to-tickets` 读它拆 ticket；`/implement` 读它获取锚点定位改动位置
- **amend**：技术方案演进时 plan.md 就地更新（不做 plan-vN 版本文件），**改动锚点随方法改名/重构同步更新**；产品需求演进时 spec 走 spec-v(N+1) 冻结
- **回写 spec**：若实现时发现 spec 的产品决策技术上不可行，**不自行变通**，走"理解纠偏"回写 spec（复用 `/implement` Step 3.5 的修正层级判断）
